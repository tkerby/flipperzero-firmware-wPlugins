## Main changes
- Current API: 88.22
- SubGHz: **Nice O-Code remotes that send the longer 72bit frame now work** - a captured remote is saved and resent at the length it actually uses, instead of a 52bit one the gate ignores. **Nice O-Code One 433MHz** is the matching Add Manually entry
- SubGHz: **Nice O-Code 112bit frames are decoded and sent** - the receiver certificate they carry is shown on the Read screen and saved with the remote, and a remote that has one broadcasts it for its first 20 presses so the receiver enrols it by itself. **Nice O-Code+Crt 433MHz** is the matching Add Manually entry
- SubGHz: Nice O-Code now sends the k byte an O-Code remote really uses, instead of the Nice One one, which was wrong on 4 parcels of every 16
- SubGHz: Nice O-Code - the certificate frame index now changes from press to press as a real remote's does, instead of repeating the same value
- SubGHz: Nice O-Code - the end-of-press marker was set on 15 of the 16 parcels, now on the last two as a real O-Code remote does. Plain Nice One and Nice FloR-S are untouched
- Apps: `Nice O-Code` can decode a saved RAW `.sub` file instead of capturing over the air, and shows the certificate next to the recovered installer code
- SubGHz Remote: **Sending button is highlighted and last pressed button details are shown** (protocol, frequency, modulation, serial, counter) instead of the D-pad
- SubGHz Remote: Hold button for endless TX, one click sends full signal (like main SubGHz app), no more forced `Repeat` value
- SubGHz Remote: RAW is sent in full with one click (Back to stop), repeats while button is held
- SubGHz Remote: Fix rolling code / custom button resets after TX, custom button no longer moves counter twice per press (same as main SubGHz app)
- Apps: `SubGHz WarDriving` - RX restarts after TX, sending a received dynamic signal no longer overwrites a saved file
- RFID: **Better FDX-B (animal chips / implants) reading** - Read now also tries 134kHz, the frequency these chips are made for, and weak signals are decoded more reliably. Also available separately in Extra Actions -> `Read FDX-B (Animals)`
- RFID: **New T5577 app - read a T5577's blocks, save them, and write them back** - the Flipper could write a T5577 but never read one, so there was no way to see what a tag held, keep a copy of it, or put a copy back. Read Tag works out how the tag reads and then reads every block of both pages; what comes back can be saved as a `.t5577` dump, looked over a page at a time with block 0 spelled out in the terms the chip reads it in, renamed, deleted, or written to a tag again. A block that was never read is kept apart from a block holding zero: the dump shows unread blocks as dashes rather than as zeroes, and a write skips them. A read that could not get the whole tag says so, and names the block it went quiet at, instead of chiming - a chip that wants a password refuses even the block 0 read the detect needs, so it reads as nothing at all, and a dump that stops part way is a tag that drifted out of the field. A write goes data blocks first and block 0 last - block 0 decides how the chip talks, and block 7 is the password it will start asking for - and the tag is then read back through the ordinary read path and compared, so "Written!" means the tag said so. A traceability block that reads back unchanged is reported as locked rather than as a failed write: page 1 blocks 1 and 2 are programmed and locked at manufacture, so a genuine chip refusing them is the chip working, and only a clone takes the write. Page 1 goes back as well - blocks 1 to 3 of it, the ones a Proxmark3 restore writes - because they hold the traceability data the chip was made with, and a copy that leaves it behind is not the same tag. The dump format is documented and parsed in `lib`, so a dump outlives the app that wrote it (by @mishamyte | PR #1179)
- RFID: **New Test Tag in the T5577 app, and setting a password is now built up one verified block at a time** - not every chip sold as a T5577 takes a write to every block: some clones implement one or two user blocks and quietly drop the rest, and a locked block looks exactly the same from the air. Test Tag finds out, one block at a time: it reads page 0, saves a backup to the card before the first write, then for each of blocks 1 to 7 flips a single bit, reads the block back, puts the original back and reads that back too - so a block that took the write is proven to have taken it, and the tag ends as it started. The verdicts fill in on screen as they are found out, a cell per block, and a block that would not go back stops the run at once and names the backup rather than walking on into the next one. A tag with a password is turned away in this version rather than tested, so every frame it sends carries none. Separately, Write and set password no longer sends a password frame to a chip that has no password yet - which a chip reads 32 bits early, writing the password word into its block 0 and leaving it silent - and no longer reports success on the strength of a read that cannot see block 7 at all: the key and then block 7 go in and are read back while the tag is still open, and only then is block 0 asked to turn protection on - and because this reader follows ASK/Manchester only, a tag it cannot read block by block is turned away rather than half written, and a configuration it will not be able to read afterwards is reported as stored but unconfirmed rather than as success (by @mishamyte | PR #1179)
- RFID: **The firmware can read a T5577 block, which is what the app is built on** - a tag's answer repeats with no frame marker, so a read cannot tell where a word begins. Block 0 settles it for itself, since it describes the modulation and bit rate its own answer arrived in, but every other block needs an anchor from outside - and the bit offset block 0 was found at is not one, because where a decoded run starts moves from read to read. Time is: the read window opens a fixed interval after the command and the tag's bit clock is divided from the field the Flipper itself generates, so the same tag bit arrives at the same time in every read, tracking the clock to within 10 us over 147 ms. Getting there needed the capture timed from the instant the window opens rather than from the first run that decoded, the settle timed to the microsecond rather than to a tick - a tick of slop is two bits of phase at RF/64, and it was moving the answer by three - and a run ended as soon as a bit arrives more than a quarter of a bit period away from where the bit before it puts the next one, since a decoder that gains or loses a bit leaves everything after it agreeing with itself while sitting a bit away from where the time says it is. The alignment is then confirmed the way a caller will use it, rather than the way it was found: block 0 is read back by address and compared against the word the configuration search recovered, and a rotation of it means the alignment is that many bits out and gets moved. Without that check the alignment came out one bit early on about a third of detects, and then every block of that read was rotated by one; since every rotation of a repeating word is also in the stream, nothing but block 0 could ever show it - a dump would come out quietly rotated, and writing it back would hand the chip a configuration it cannot answer in. An erased block is the one case needing care either way: the tag sends the same waveform for 00000000 and FFFFFFFF, and only the alignment tells them apart (by @mishamyte | PR #1179)
- RFID: **Wipe T5577 and Clear T5577 Password now check the tag instead of assuming** - both used to be blind. The wipe watched for six seconds to see whether the tag still read as anything and called silence a success; Clear Password announced "Success!" whichever password it had tried, including when none of them fit. Both now write a block and read it back, so the verdict is the tag's own answer, and both show what they are doing while they work. The wipe writes its eight blocks one at a time behind a progress bar and leaves Proxmark3's own blank configuration, so a tag wiped by either tool looks the same to the other; when it cannot confirm, it says whether the tag went quiet or answered with something else, and points at Clear Password for the former, which is what a password looks like from here. Clear Password tries the tag as an unprotected one first, three times, then the custom password, then the shipped list - stopping at whichever works. Stopping matters: every attempt after the tag is already open sends a password frame that an open tag reads off the wrong bit positions, and a third of the list would set block 0's lock bit permanently if it did. It no longer writes the password block at all, since clearing the password bit in the configuration is what opens the tag. Both now live in the T5577 app as **Wipe Tag** and **Clear Password** rather than in RFID -> Extra Actions, since neither has anything to do with a key: they address blocks and are judged by reading one back. The passwords Clear Password sweeps moved with them, out of the firmware and onto the card as `/ext/lfrfid/assets/t5577_dict.lfrfid` - one hex word per line, the same shape as the NFC key dictionaries - so a word found after this release can be added without new firmware, and a missing file says so instead of reporting that none of them matched. The honest cost is time - a password that is not in the list now takes about a minute and a half, where before it took ten seconds and then claimed success regardless - so the screen names the candidate it is on and Back stops it at once. Getting the read to work at all needed the reader's own comparator offset measured and subtracted: it reports every high half-bit longer than it is by 50-70 us, which is a fifth of a half-bit at RF/64 and half of one at RF/32, and without that correction the shorter rates do not decode (by @mishamyte | PR #1179)
- RFID: **Write and set password no longer hangs with the tag already protected** - the screen stayed on "Writing with password" while the tag came away locked. The step that proves protection took waits on the shared LF reader, whose timeout restarts whenever any decoder produces a frame rather than bounding the read, so a tag two decoders disagree over keeps it waiting for ever. Reads that something is waiting on now carry a deadline as well, and the screen names the stage it is on - writing the key, storing the password, turning it on, checking - so a run that takes ten seconds over five block reads no longer looks like a run that died. The same wait sat under the ordinary Write verify, which is fixed with it (by @mishamyte | PR #1179)
- RFID: T5577 app - the backup a Test Tag run saves is deleted when the tag is proven back to what it held, and kept only when a block was not restored. A dump of a tag that is already fine, under a name every run reuses, is the one a user would write to the next tag they test; starting a test while one survives now warns before overwriting it (by @mishamyte | PR #1179)
- Apps: Build tag (**18oct2026**) - **Check out more Apps updates and fixes by following** [this link](https://github.com/xMasterX/all-the-plugins/commits/dev)
## Other changes
- OFW: FatFs: apply upstream R0.12c patches, fix 0-byte files in fragmented exFAT directories
- API: Export `faac_slh_reset_prog_mode` for apps
- iButton: Fix write success text going off screen
- RFID: Move Writing screen text up so long file names fit
- RFID: ~1 KB of flash freed - the write_data bodies that were near-identical across 20 of the LF protocols (viking and jablotron differed in four constants, six carried the same 64-bit reversal loop) now share one implementation per chip, and the block count is read from the config word instead of being passed beside it (by @mishamyte | PR #1183)
- Core: **~7 KB of flash freed** - number parsing no longer pulls in newlib's arbitrary-precision machinery for hex floats and inf/nan literals, which nothing passes it. Float fields in `.ir`/`.sub`/`.nfc` files read back exactly as before; doubles are within 4 ulp (by @mishamyte | PR #1186 | Closes #1184)
